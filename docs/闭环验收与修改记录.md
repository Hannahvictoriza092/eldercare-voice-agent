# 三个 Skill 数据闭环：修改记录与验收

更新日期：2026-09-26。

## 目标

两个上游写业务记录 → health_report 下一次查询可见 → 正确生成周报 → 保存并重载档案。
“实时”指成功写入后的下一次查询可见，不是消息推送或后台自动生成报告。

## 第一步：共享事件流刷新

文件：common/event_store.py。

- all、medication_logs、incidents 查询前重新读取 JSONL。
- 加载时重建缓存，同 ID 最后一条覆盖之前状态；文件清空或删除后不残留旧记录。
- upsert 先完成文件追加，再更新内存，避免失败写入先污染内存。
- 不要求三个模块持有同一内存实例，只要求它们指向同一事件文件。

验证：先初始化读方，再由另外两个实例写入与更新，读方能直接看到变化。

## 第二步：报告与摘要口径

文件：skills/health_report/executor.py、messages.py、skill.py、schema.py。

- 周报和发送动作仅在服药、异常两类记录均为空时返回数据不足。
- 仅有呼救记录时照常生成周报、通知及档案，服药部分注明暂无记录。
- 摘要与周报复用统计逻辑；新增 skipped、pending，完整区分记录状态。
- 输出新增 record_count（已有记录数）、taken_ratio（已服记录占比）。
- 为兼容旧 API 和档案，保留 planned、adherence 同值字段；它们不表示应服次数和按时率。
- 正文不再称“按时完成”；补服计入已服，但不认定为按时。
- 缺服药数据的周不比较服药改善；异常事件仍可作跨周比较。
- send_report 返回 notification_pending=True；话术改成待发送，实际送达由出站层处理。

补充修复：skills/medication_reminder/store.py 只在已服状态填 taken_at，
漏服/跳过不再把记录创建时间当成实际服药时间。

## 第三步：可重载的档案

文件：skills/health_report/store.py。

- 从 JSON 加载时显式恢复 WeeklySnapshot 对象，并按周排序。
- 兼容缺少 skipped、pending 的旧档案，默认值为 0。
- 保留同一老人同一周覆盖更新行为；重复生成不会堆积重复快照。
- 写入采用临时文件替换，降低中途写入留下半个 JSON 文件的风险。
- 查询档案输出包含新口径字段；仅呼救档案的口语摘要也保留异常数量。

## 第四步：自动验收

新增 tests/test_skill_pipeline.py，真实调用上游业务，不只向报告模块注入预制结果。

| 场景 | 期望结果 |
|---|---|
| 三个模块预先初始化，确认一次服药、调度产生一次漏服、发起一次呼救 | 记录 2、已服 1、漏服 1、异常 1 |
| 重复调用漏服调度 | 无重复记录，无新的漏服通知标记 |
| 呼救推进至已接单、在途 | 仍为 1 起，保留三步状态历史 |
| 补报漏服那次已服 | 记录仍为 2、已服变为 2、漏服变为 0 |
| 重建三个模块后再次生成/查询 | 统计不丢失，同周快照仍只有 1 份 |
| 下一周产生新记录 | 从重载档案读上一周，正常输出趋势 |
| 只有呼救记录 | 可生成、产出待发送通知、归档并重载 |
| 两类记录都为空 | 提示未知，不生成通知，不创建空档案 |
| 不同老人、不同周 | 数据和档案不混入 |
| 跳过、待确认记录 | 独立计数，保存后可恢复 |
| 历史格式档案 | 恢复为类型化快照，同周更新不报错 |

tests/test_event_store.py 新增独立实例刷新和清空缓存的回归测试；
tests/test_health_report.py 将旧“依从率/按时”话术断言改为准确口径，并验证待发送状态。

~~~bash
python -m pytest tests/test_skill_pipeline.py tests/test_event_store.py tests/test_health_report.py -q
python -m pytest -q
~~~

本次验证：全量 119 个测试通过（原有 112 个 + 新增 7 个）。

## 当前边界

JSONL 每次查询全量重读，当前定位是小规模单进程串行使用；未加入并发写锁或跨文件事务。
定时漏服调度仍由上层调用，也未补齐全部应服记录，因此不能把记录占比当成真实按时率。
档案默认由单个报告服务维护；多个活跃档案写入器的并发一致性不在本轮范围。
历史周报是生成时的快照，上游补报后须重新生成该周报告才能更新档案。
电话、短信、Qwen、ASR/TTS 和常驻后台调度均不属于本次闭环验收范围。
