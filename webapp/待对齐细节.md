## 🔴 一、`confirm_level` 三个 skill 没统一（最要紧）

**约定怎么说的**

- `docs/接口约定.md` 第三节：`confirm_level` 是「执行前需要的确认强度」，
  Agent 层据此决定要不要让老人复述、要不要通知家属
- `docs/接口约定.md` 第七节：`SkillResult` 增加 `confirm_level` / `notifications`
  字段 —— 状态写着「已定稿，三个 skill 已统一改用」

**实际现状（对不上）**

| skill | 有没有设 `confirm_level` | 证据 |
|---|---|---|
| 用药提醒 | ✅ 有两处 | `skills/medication_reminder/executor.py:168` 设 `REPEAT_BACK`（取消提醒）<br>`skills/medication_reminder/executor.py:348` 设 `GUARDIAN`（漏服升级） |
| 呼救 | ❌ 从未设置 | `skills/emergency_call/executor.py` 全文无 `confirm_level` |
| 健康反馈 | ❌ 从未设置 | `skills/health_report/executor.py` 全文无 `confirm_level` |

**为什么这是问题**

不设置就走默认值 `ConfirmLevel.NONE`，Agent 层会认为「不需要任何确认」。
但呼救的两个动作本身是不可撤销的：

- `emergency_call/cancel`：老人说「按错了」是第一次表述，此时 `confirmed=False`，
  直接取消会导致**真正需要救助的呼救被误取消**
- `health_report/send_report`：会真的把健康周报发给医生/子女，发出去了收不回来

**建议改法**

```python
# skills/emergency_call/executor.py 的 cancel()
# 第一次说「按错了」时（confirmed=False）要求老人复述确认
confirm_level=ConfirmLevel.REPEAT_BACK if not params.confirmed else ConfirmLevel.NONE

# skills/health_report/executor.py 的 send_report()
confirm_level=ConfirmLevel.REPEAT_BACK   # 发送前让老人确认接收方
```

**待讨论**：`GUARDIAN`（通知家属）目前只有漏服用。呼救的 `trigger` 要不要也设 `GUARDIAN`？
设了意味着 Agent 必须通知家属；不设意味着只产出 Notification 但不强制。**这条要一起定。**

- [ ] `emergency_call/cancel` 补 `confirm_level`
- [ ] `health_report/send_report` 补 `confirm_level`
- [ ] 定 `emergency_call/trigger` 的级别

## 🔴 二、通知的「出站层」不存在

**现状**

三个 skill 都按约定产出了 `Notification` 对象（只产出、不发送），
但**没有任何代码负责真正发送**，也没有送达确认和重试：

| 产出方 | 证据 |
|---|---|
| 呼救（3 处：trigger / cancel / confirm_safe） | `skills/emergency_call/executor.py:82, 119, 144` |
| 健康反馈（1 处：send_report） | `skills/health_report/executor.py:374` |
| 用药提醒（漏服升级） | `skills/medication_reminder/executor.py` 的 `get_due_reminders()` 返回 `notify_text` |

`common/domain.py` 里 `Notification` 定义了 `sent_at` 和 `delivered` 两个字段，
**全仓库没有一行代码给它们赋值**。

**为什么这是问题**

呼救场景下这是**安全相关**的：老人摔倒后说了「救命」，系统记录了一条 `Notification`，
但没有任何东西把它发出去。演练时必须能说清楚「这一步之后谁负责发」，
否则演示会被问住。

**要一起定的三件事**

1. 出站层放在哪个模块、谁负责写
2. 三种目标（`family` / `hospital` / `community` / `emergency`）分别走什么通道
   （短信？微信？APP 推送？电话？）—— 这条 `docs/接口约定.md` 第七节也还挂着
3. 发送失败怎么办、多久重试、什么算送达

**最低限度**：哪怕这学期不做真实发送，也要**在文档里明确写「本阶段不发」**，
并说明演示时看到的是「待发送队列」。

- [ ] 定出站层归属与接口
- [ ] 定各目标的通道
- [ ] 定失败重试 / 送达确认策略

## 🟠 三、`Person.emergency_contacts` 定义了，但呼救没用

**现状**

- `common/domain.py` 定义了 `Contact`（姓名/电话/关系/是否首要）和
  `Person.emergency_contacts: list[Contact]`
- 但 `skills/emergency_call/executor.py:18` 用的是**写死的常量**：

```python
TARGETS = [NotifyTarget.FAMILY, NotifyTarget.COMMUNITY, NotifyTarget.EMERGENCY]
```

**为什么这是问题**

真实场景必须按老人**自己的**联系人来发：先打儿子还是先打社区？电话号码是多少？
现在这套写死的目标，出站层拿到了也不知道该打给谁。

**建议改法**

呼救 `trigger` 时从 `Person` 取 `emergency_contacts`，按 `is_primary` 排序决定通知顺序；
`Person` 为空时回退到现在的默认 `TARGETS`。

**待讨论**：`Person` 里同时有 `guardian_id` 和 `emergency_contacts`，
两个都表示「找家属」，关系没说清 → 需要定一个为准。

- [ ] 呼救改为读 `Person.emergency_contacts`
- [ ] 定 `guardian_id` 与 `emergency_contacts` 的关系

## 🟠 五、跟 ASR 那一组的对接契约

**现状**

我们这条链路假设的输入是「**一句完整、已纠正的文本**」。
但另一组还在做老年语音识别实验（`SeniorTalk` 数据集），输出形态未知。

**要一起定的**

1. ASR 输出格式：纯文本？带时间戳？带说话人分离？（他们工作区在做 speaker_disjoint，
   说明**有说话人概念**）
2. 会不会分句：老人一句话里夹两个意图（「我头晕，今天药还没吃」）怎么切、谁切
3. **错别字怎么处理**：老人语音识别最容易错的是**药名**。药名错一个字，
   整个用药提醒就废了。是我们这边做纠错，还是 ASR 那边给候选？

**这条建议**：等他们实验出结果再谈细节，但**现在就要把「输入是一句话文本」
这个假设写下来**，让对方知道我们依赖什么。

- [ ] 约定 ASR 输出格式
- [ ] 定分句 / 多意图的归属
- [ ] 定药名纠错由谁做

## 另：演示本身暴露的一个正面结论

三个 skill 的**共享事件流是真实生效的** —— 网页演示里先设置用药提醒、再报吃药、
再发呼救，然后问「我这周吃药按时吗」，健康反馈能真的读到前面产生的数据
（`adherence: 100.0%`、`incidents: 1`）。这条链路没问题，可以放心往上盖东西。
